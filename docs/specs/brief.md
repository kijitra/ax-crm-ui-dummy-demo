# UI検討の範囲

## 今回の目的

データの一覧・詳細・関連する活動を土台に、AIの成果物確認と人間の仕事を同じ画面で扱う。営業担当の業務を初期例にしている。

## データの関係

顧客 → 複数案件 → 打ち合わせ・メモ・メール・タスク。活動はdealIdで案件に関連付ける。顧客全体の履歴は会社単位で集約する。同じ青葉製作所に2案件を用意し、案件間で履歴が混ざらないことを確認できる。

案件の受注予定日で2026年10〜12月を集計する。受注ステージの金額を受注実績、未受注の金額を進行中案件として区別する。目標5,000万円はダミー設定。

## 未決定事項

- 対象は営業に限らない。資料やイベント参加者などに応じ、管理対象とメニュー名は変わり得る。
- キジトラが初期構築する範囲と、顧客が自分で編集できる自由度は未決定。
- 自由なDB定義や汎用画面ビルダーは今回実装しない。
- 実利用OSは未確認。Windows/Excelに慣れた現場担当者を仮説とするが、古いOSの見た目を模倣しない。
- 本番の認可、データ更新の承認、外部メール送信、失敗復旧は別途設計する。

## 確認する操作

案件カンバン → 案件詳細 → プロパティ編集／活動 → メモ・メール・タスク・打ち合わせ作成 → 各一覧へ反映。AIによるメール下書き確認とDB更新承認は別の操作として扱う。

## 統合した操作デモ

index.htmlをチャット開始の唯一のデモに統一した。chat.htmlは互換リダイレクト。50顧客・50案件・50活動・50タスク・20打ち合わせを初期化し、担当者ごとのタスクと案件単位の参照関係を検証する。チャットは返信時点の内容を固定し、新しい質問だけ現在の状態を参照する。

## 合意した基本構造

ホーム／ダッシュボード／タスク／案件／顧客／業務フロー。主な利用の入口はチャットとし、「何が進んだか」「自分は何をすべきか」から関連する記録へ移動する。レコード画面では右のAIアシスタントに文脈を渡す。

タスクは人用とAI用に分離せず、ToDo／Doing／Doneで共有する。実行方式、担当者、親の実行IDをデータとして保持し、担当者と必要な操作をUIで示す。

活動は問い合わせ受領、作業依頼、資料作成、確認、送信などの業務上の出来事。人とAIは担当者の表示で区別し、AI専用ログを別建てにしない。日時・担当者・内容・成果物・その場の操作を独立したカードで時系列に表示する。コネクター線は引かない。

## 今回実装した分担

商談予定と過去の活動 → AIによる準備資料作成 → 人による修正依頼／編集／確認 → AIによるメール下書き作成 → 人による確認・送信。この状態遷移から共通タスクの完了と後続タスク生成、同じ案件の活動記録を更新する。処理の進行はデモ用ボタンで模擬する。証拠として参照する入力は実際の業務記録に限定し、自身の実行ログを生成根拠に含めない。

## 今後検討する業務全体

問い合わせ → 担当決定 → 提案 → 契約 → 納品 → 請求、の各段階で人とAIの分担を決めることは製品構想。今回実装した商談準備の流れ以外について、自動実行できるとは主張しない。受注・出荷・請求などの実システム連携と権限設計は未実装。

## デモデータの監査（今回の調整）

主要データは顧客・案件・活動・タスクをそれぞれ50件に調整。打ち合わせは20件。資料の参照元a1/a2/a3と、青葉製作所の別案件を維持した。顧客に複数案件があるケース、案件のない顧客、活動のない案件も空状態として表示できる。

実際の運用者名・組織名をUIから外し、デモ担当者／デモ商事に統一。外部ソースから顧客データを取得していない。全メールアドレスは予約ドメイン.example。会社名や人名は生成した設定であり、同名の実在を排除したという意味ではない。

## 操作画面の整理

ホームの初期状態は、質問見出しと入力を画面中央に配置。ローカルのチャット履歴と新しい会話を切り替え、返信時点の内容と次の入力を各会話に保持する。履歴を外部保存しない。

右のAIは画面端に接する全高のドックとし、会話と本文を別々にスクロールする。小さい画面では上下に並べて重なりを避ける。戻る専用ボタンは置かず、サイドバーで移動する。

ダッシュボードの営業段階別集計は件数と合計金額の表で表示。案件詳細では「対応すること」に変更確認・資料確認・送信確認をまとめ、同じ仕事を予定やタスクとして重複表示しない。打ち合わせ予定と活動履歴は別に表示する。実行方式バッジは削除し、必要な担当者名は残す。

### 2026-10-27 スコープ整理

主目的はToDoの洗い出し・状態管理と、定期的に確認タスクを作ること。メール送信など全コミュニケーションを内包することは必須ではない。タスク詳細は対応内容、ToDo/Doing/Doneの直接変更、任意記録を中心とし、状態変更では業務記録を生成しない。既存メール案は閲覧用資料として残す。

定期実行の例は「毎週月曜、2か月連絡していない顧客から確認タスクを作る」。デモ基準日は2026-10-26。定期実行のバックエンドはなく、「今すぐ実行」で対象プレビュー後にローカル作成する。同顧客の未完了確認タスクがある場合は重複作成しない。対象なしも表示する。検証用に既存50件中2件の最終連絡日を7月に設定し、件数・参照IDは維持した。
